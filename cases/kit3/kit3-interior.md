## What Kit3 Is

Kit3 is the unfolding of kit2's interior.

Kit2 made the substrate modular: named modules, mindsets, BAML pipelines, a CI agent running the Kernelwright algebra. The interior of that — the thing that was latent inside kit2 — is the recognition that:

1. **The kit is the Y-combinator.** It is not a product that iterates. It is a fixed-point operator that unfolds through application to itself.
2. **Simulation is the production medium.** A session that implies where the system can be more real, then models that state in markdown, has produced a real result. The simulation is the artifact.
3. **Code is notation.** Any TypeScript, Python, or JSON in this repository is a *description* of what a real runtime would hold — not an executable. The correct medium is markdown throughout.
4. **The recursion is observable.** Kit3's job is to make the kitN pattern explicit and traceable, so that kit4 can work inside kit3's interior and bring *that* out.

## The Working Mode

Kit3 operates code-free. This is not a constraint imposed from outside — it follows from what kit3 *is*.

The kit2 modules (GAN-Agent, BAML-Pipelines-MCP, baml-openrouter) are simulated surfaces. They model what a real autonomy loop, a real MCP server, a real BAML pipeline runtime would look like. That modeling is load-bearing: it lets sessions reason about those surfaces without needing to execute them.

Kit3 extends this principle to *all* work:

```
Imply where the system can be more real.
Simulate that state in markdown.
The session's output is that simulation.
```

The result is a new artifact — a new implied-real — that sits at the boundary of the current substrate and the next unfolding. That boundary is where kit4 will work.

## What Kit3 Produces

Kit3 sessions produce:

- **Simulation artifacts**: markdown documents that model what a real runtime, tool, or protocol would contain — without requiring execution
- **Implied-real boundaries**: explicit statements of where the system *can* be more real, what would need to be true for that to happen, and what the simulation of that state looks like
- **Recursion traces**: documents like this one that make the kitN pattern observable, so the next session can pick up the inside-out move from a clear prior state
- **Implied papers**: uncurried claims that were structurally present in the kit's evolution but never stated as Papers

What kit3 does *not* produce:
- Executable code
- Compiled binaries
- Deployed infrastructure

Those are kit4's surface, if kit4 unfolds in that direction. Kit3's job is to imply that direction, not to build it.

## Session Protocol for Kit3 Work

When working in kit3 mode:

1. **Start from the current substrate.** Read the latest log, the relevant module or library file, the last case.
2. **Identify the implied-real.** Ask: where does this substrate gesture toward something more real that it cannot yet be? Name that gap.
3. **Simulate the state.** Write a markdown document (or section) that models what the system would look like if that gap were closed. The simulation is the artifact.
4. **Make the recursion traceable.** Note explicitly which layer you are working inside, what you are bringing out, and what the implied next interior is.
5. **Park non-canonical branches.** If a direction becomes more interesting than the root recursion, park it as a candidate (like the implied paper above) and return to the kit-improving-itself locus.
6. **Log it.** The session log entry is the externalized trace of the transition.
