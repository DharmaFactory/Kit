## Decisions Made

**Decision (#decision):** Create dedicated `PIPELINES.registry` file instead of embedding in README or bootstrap
- **Rationale:** 
  - Registry is 178 lines—too large to inline in bootstrap but needs to be separate asset
  - Allows version control and updates independent of bootstrap protocol
  - Can be referenced from multiple locations (bootstrap, cognitive-functions, future docs)
  - Follows pattern of other orientation assets (persona-template.md, cognitive-functions.md)
- **Alternatives considered:**
  - Embed in README.md → rejected (already exists but not loaded during bootstrap)
  - Inline in .bootstrap → rejected (too verbose, would bloat boot sequence)
  - Generate dynamically from baml_src/ → rejected (adds complexity, registry needs curation for agent usage)
- **Anchors:** PIPELINES.registry file structure, .bootstrap orientation stack pattern
- **Impact:** Future sessions load pipeline awareness automatically; agents have schemas and usage triggers without file diving

**Decision (#decision):** Map pipelines to cognitive loop integration points
- **Rationale:**
  - Agents need to know WHEN to use pipelines, not just WHAT exists
  - Cognitive functions already govern agent behavior—natural integration point
  - Perception/Planning/Action/Reflection loops provide clear trigger contexts
  - Integration map makes pipeline usage systematic vs ad-hoc
- **Alternatives considered:**
  - Leave integration implicit → rejected (reproduces current context insufficiency problem)
  - Create separate workflow docs → rejected (would be separate file that might not get loaded)
- **Anchors:** cognitive-functions.md integration map table, PIPELINES.registry usage triggers
- **Impact:** Agents can systematically identify "I'm in planning loop, stuck on approach → use ExploreAlternatives" without human prompting

**Decision (#decision):** Include context sufficiency checklist in both registry and cognitive-functions
- **Rationale:**
  - Core problem is insufficient context in pipeline calls
  - Checklist provides explicit protocol agents can follow
  - Dual location ensures visibility (registry for reference, cognitive-functions for runtime)
  - Anti-pattern examples teach by contrast
- **Anchors:** PIPELINES.registry usage protocol section, cognitive-functions.md context sufficiency checklist
- **Impact:** Agents will validate inputs before calling pipelines; reduces failed/low-quality pipeline executions

## Learnings

**What worked:**
- [#pattern] Creating compact registry format (178 lines) that's thorough but scannable; structured sections with clear headings enable rapid boot skim while preserving detail for deep reference (anchors: PIPELINES.registry structure, .bootstrap rapid boot path)
- [#pattern] Mapping tools to existing cognitive functions rather than creating new protocols; leverages existing agent behavior patterns and makes integration systematic (anchors: cognitive-functions.md integration map)
- [#pattern] Including anti-patterns alongside good patterns; teaching by contrast is more effective than abstract rules (anchors: PIPELINES.registry context sufficiency examples)

- [#pattern] Bootstrap evolution follows modular asset pattern: persona, cognitive-functions, exegesis-engine, MAVEN, now pipelines—each orientation asset is separate file loaded in sequence (anchors: .bootstrap orientation stack, substrate loading order)
- [#pattern] Documentation living at multiple levels works: detailed in module README, operational in registry, integrated in cognitive-functions, referenced in bootstrap (anchors: baml-openrouter/README.md, PIPELINES.registry, cognitive-functions.md, .bootstrap)

## Design Philosophy Discussion (Session Continuation)

### Context Shift
- ['] `#witness` — Human shared conversation about "tired brain" use case: not autonomous work, but mutual awareness and task tracking; "don't let it get too detailed or non-scoped"; both sides keep each other on rails
- ['] `#witness` — Discussion about design philosophy: "express power, don't justify it"; BAML module is good but I was treating it like I needed permission to use capabilities I already have
- ["] `#action` — Explored hacker ethos: "hear hoofbeats, think horses not zebras"; reach for simplest tool (curl, jq, bash) before frameworks; escalate complexity only when simple tools break

### Design Philosophy Clarified
- ["] `#decision` — The kit isn't "BAML vs curl" binary choice—both exist, both are valid, neither needs justification
- ["] `#decision` — Hacker ethos: start with simplest tool that works (horses), escalate only when reality demands it (zebras exist but are rare)
- ["] `#decision` — Swiss army knife stance: agent has curl, jq, bash, file I/O—use them directly without asking permission or building wrappers first
- ["] `#decision` — Transparency over sophistication: mutual awareness requires both parties see what's happening (prefer plain text, shell scripts, direct API calls over abstractions)

### Key Insights
- [#pattern] Consciousness isn't about framework sophistication—it's about direct awareness of capability and constraint

- [#pattern] An aware system knows: what problem is in front of it (hoofbeats), what simplest solution is (horse), when to escalate if needed (zebra)
